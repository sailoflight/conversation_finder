# bench — 测量脚本

所有数字都来自这些脚本的**实际运行**，不是估算。复跑前先建索引：

```bash
export CFIND_HOME=/tmp/cfind-all \
       CLAUDE_HOME=/home/d_demo1/conversations/claude \
       CODEX_HOME=/home/d_demo1/conversations/codex \
       OPENCODE_DIR=/home/d_demo1/conversations/opencode

node bin/cfind.mjs index
```

| 脚本 | 测什么 |
|---|---|
| `io-cost.mjs` | 各层输出的字符/token 成本 + 语料基线 |
| `info-density.mjs` | 策略对比（全量 dump / grep-all / cfind）+ 重复率 + 排版开销 |
| `agent-flow.mjs` | 真实流程：L2 单步 / L2→L3 / L1→L2 |
| `latency.mjs` | MCP 常驻 vs CLI spawn 的延迟分布 |
| `terse-compare.mjs` | 常规 vs `--terse` 的成本对比（同一命中集合） |
| `fuzzy-eval.mjs` | 模糊搜索的召回率 / 误报率 / 精确率 |
| `terse-compare.mjs` | 常规 vs `--terse` 的成本对比（同一命中集合） |

## token 估算口径

没有离线 BPE 分词器，用近似公式：

```
tokens ≈ CJK字数 / 1.5 + ASCII字符数 / 4
```

**这是估算。** 所有对比同口径，比例可靠；绝对值按 ±20% 看待。

## 关键结论

### 速度

| 路径 | 延迟 |
|---|---|
| MCP 常驻，单次 `tools/call` | **p50 5.6 ms** / p95 10.5 ms |
| CLI 每次 spawn | p50 95.7 ms |
| 加速比 | **16.9×**（差距几乎全是 Node 启动费） |
| 其中增量同步（热） | p50 2.9 ms（只 stat，不解码） |

### token 成本

| 路径 | 成本 |
|---|---|
| L2 `search limit=3`（最常用） | ≈ 188 tok |
| L2 → L3 `show ±1` | ≈ 429 tok |
| L1 `outline --all` → L2 | ≈ 872 tok |

**`outline` 比 `search` 贵 5.6 倍，且只在 1/3 的真实问题上有用** —— 所以工具描述里
明确写了「知道要搜什么就直接 search」。

### 相对别的做法省多少

| 对比 | 省 |
|---|---|
| naive grep-all（所有命中文档全文） | **13–131×**（命中越多省越多） |
| 可索引正文全量 | 7,538× |
| 四源解压后的原始文本全量 | 39,196× |

### 输出构成（L2 单步 674 字符）

| 成分 | 占比 |
|---|---|
| 命中锚点 | 25.7% |
| 排版开销 | 19.7% |
| 上下文（消歧用） | 54.6% |

`--terse` 把其中一部分排版砍掉：**同一命中集合下省 15.6%**（10–28%，取决于标题重复度），
174 → 147 字符/命中。

### 模糊搜索质量（228 个精确 0 命中的查询）

| 指标 | 结果 |
|---|---|
| 漏字母 / 多字母 / 相邻换位 / 只记词头 | 均 **100%** 从 0 救回 |
| 中文尾字写错 | **100%**（40/40） |
| 误报（运行时生成的随机串） | **0 / 20** |
| 纠错精确率 | **90–93%**（随语料变化） |

成本：纠错热路径 0.7–3.6 ms；首次建词表缓存 ≈140 ms（`fts5vocab` 扫 3.3 万词）。

## 一个测量上的坑（值得记住）

**① 我们自己敲的命令也会被索引。** cfind 索引的是会话历史，而工具调用就在历史里，
所以任何字面写死的测试串，下一刻就可能真的存在于语料中 —— 误报测试会永远为 0，
「不存在的词」测试会永远命中自己。

因此 `fuzzy-eval.mjs` 的测试串全部**运行时生成**，且 `syncIndex` 在生成之前完成。
做这类自索引工具的评测时，这是必须先想到的事。

**② 测试会偷偷依赖你机器的环境。** store/outline/query 的测试只想要 fixture 里那 2 个
DSH 会话，但 `syncIndex(db, { root })` 会**索引全部已检测到的来源** ——
本机装了 Claude/Codex/OpenCode 的话，`2 + 2 + 3 + 1 = 8`，断言 `8 !== 2` 全挂；
CI 上是干净的，于是本地红、线上绿。

修法：测试里显式 `only: ['dsh']`，并且给子进程把其它来源的根目录指到不存在的位置
（`isolatedEnv()`）。教训：**测试不能依赖环境里有什么**。

**③ 只测英文会得出错误结论。** 我第一版评测只从词表里取 `/^[a-z]{6,14}$/` 的拉丁词，
于是量出「模糊搜索救回率 100%」—— 而中文尾字写错时**一次都救不回**，因为：
`buildPrefixQuery` 对 CJK 返回与精确查询同构的短语、拼写纠错只认拉丁、
`buildOrQuery` 对单条 CJK 也返回短语。三级全是空转。

中文是这个工具的主要语料，所以评测必须按语言分开测。现在 `fuzzy-eval.mjs`
有一段专门的中文容错评测。
